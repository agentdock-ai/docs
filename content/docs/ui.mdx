---
title: Agentdock UI
description: Editable React chat components connected through your application's adapter.
---

Agentdock UI adds a chat interface to your Agentdock application. The installer
copies small, editable components into `components/agentdock-ui`; the
`@agentdock-ai/react` npm package provides the store, hooks, event decoding, and
render model. Your application owns network requests and authentication.

The data flow is: the Chat component calls your `ChatAdapter`; the adapter sends
the app's request; your server authenticates it and invokes Agentdock; Agentdock
streams canonical events; the adapter decodes and yields those events; the UI
store updates its render model and Chat displays it. The UI never chooses your
endpoint or request format.

## Install the chat

From your React application's directory, run the published installer:

```sh
npx @agentdock-ai/agentdock-ui add chat
```

The installer detects npm, pnpm, Yarn, or Bun, checks required dependencies and
versions, and installs missing dependencies with the detected package manager.
It copies the matching Radix or Base UI source into your app, where you can
edit it normally. Node.js 22 or later, React 18 or later, and TypeScript are required, along with
Tailwind CSS 4, a resolvable TypeScript alias, and shadcn semantic theme tokens.
An existing `components.json` selects Radix or Base UI primitives. If that file
is missing, the installer can create it using the detected alias and theme.

Use `--cwd ./apps/web` to target an app in a monorepo, or add `--dry-run` to
preview changes without writing files or installing dependencies. Repeated
installs preserve edited source; `--overwrite` explicitly replaces consumer
edits. For a Starter checkout, run `npm run ui:add` from its root.

The editable Chat files are copied into your project; they are not imported as
a prebuilt component package. The runtime dependency is `@agentdock-ai/react`.

## Connect your adapter

`Chat` has no endpoint prop. Supply a stable `ChatAdapter` whose `sendMessage`
yields canonical Agentdock events. The request body below is an example of an
application-owned API, not a built-in Agentdock envelope.

```tsx
import { Chat } from "@/components/agentdock-ui/chat";
import { decodeAgentEventStream, type ChatAdapter } from "@agentdock-ai/react";

export function createChatAdapter({
  endpoint,
  threadId,
  request,
}: {
  endpoint: string;
  threadId: string;
  request: typeof fetch;
}): ChatAdapter {
  return {
    async *sendMessage({ text, signal }) {
      const response = await request(endpoint, {
        method: "POST",
        headers: { "content-type": "application/json" },
        body: JSON.stringify({ prompt: text, threadId }),
        signal,
      });
      if (!response.ok || !response.body) throw new Error("Request failed.");
      yield* decodeAgentEventStream(response.body, { signal });
    },
  };
}

// Construct once for the app's current conversation.
<Chat adapter={chatAdapter} />;
```

Your server validates requests, authorizes and derives thread identity, then
calls `runtime.pipe()` or `runtime.toResponse()`. Browser consumers receive the
canonical event contract; normalize provider and LangGraph events on the server.

### Events and trusted context

`sendMessage` must yield canonical `AgentEvent` values. For an SSE response,
`decodeAgentEventStream(response.body, { signal })` parses and validates each
event. The Chat component consumes the iterable into its `AgentStore`, which
reduces events into UI state and the ordered render model. Do not yield raw
provider or LangGraph events; map them through Agentdock on the server.

The `context` passed to `runtime.pipe()` is trusted, server-side graph context.
It is separate from browser UI state and from the event stream. Derive identity
and permissions on the server, then pass only the authorized context to the
graph. For example:

```ts
await runtime.pipe(response, {
  threadId: authorizedThreadId,
  input: { messages: [{ role: "user", content: prompt }] },
  context: { userId: authenticatedUser.id },
});
```

The `prompt` and `threadId` in the earlier adapter example show one possible
application API shape; use your server's actual contract and never trust an
unverified client-supplied thread ID.

### Adapter capabilities

`sendMessage({ text, attachments?, signal })` is required and returns an
`AsyncIterable<AgentEvent>`. The UI creates and aborts the signal for the
operation. Keep the adapter stable while a run is active; recreate it only when
its actual configuration changes.

| Optional member      | Implement it when                                                 | Adapter contract                                                                                                                                                                         |
| -------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cancelRun`          | Your server can stop active work.                                 | Receives `{ runId, signal }`; sends the cancellation request and resolves when it is accepted.                                                                                           |
| `respondToInterrupt` | Your graph supports pending interrupts or approvals.              | Receives `{ runId, interruptId, decisions, signal }`; returns canonical events for the resumed run. `runId` can be `null` for hydrated pending state.                                    |
| `continueRun`        | Your graph can continue a static pause with no pending interrupt. | Receives `{ runId, signal }`; returns canonical events. `runId` can be `null` after history hydration.                                                                                   |
| `attachments`        | Your app supports file or image upload.                           | Set optional `accept`, `maxFiles`, and `maxFileSize`, and implement `upload({ file, signal })`. Return `{ id, name, size, content }` with an app-owned ID and canonical display content. |

Add only capabilities that your server implements. The component hides actions
whose adapter methods are absent. The host must authorize each action and verify
that uploaded attachment IDs belong to the current user and conversation.

For a server using `@agentdock-ai/conversations`,
`createConversationClient()` can provide a ready adapter and thread/history
methods. It expects that package's documented HTTP routes; it does not create
those routes on your server. Supply an authenticated `fetcher` when needed. See
the [`@agentdock-ai/react` README](https://github.com/agentdock-ai/agentdock-ui/tree/main/packages/react#conversation-api-helpers)
and [`@agentdock-ai/conversations` README](https://github.com/agentdock-ai/agentdock/tree/main/packages/conversations).

For example, if those routes are mounted under `/api` and your app already has
an authenticated fetch function:

```tsx
import { createConversationClient } from "@agentdock-ai/react";

const client = createConversationClient({
  baseUrl: "/api",
  getThreadId: () => selectedThreadId,
  fetcher: authenticatedFetch,
});

<Chat adapter={client.adapter} />;
```

Use the returned client methods to list or create threads, rename them, and load
history. Your app still owns authentication, access checks, route mounting, and
the selected thread state.

## Configure the Chat component

The copied `Chat` component includes its own `AgentProvider`; pass it the adapter
and optionally a long-lived `AgentStore`:

```tsx
<Chat
  adapter={chatAdapter}
  welcomeTitle="How can I help?"
  welcomeDescription="Ask a question or choose a suggestion."
  suggestions={["Summarize this", "Find an answer"]}
  placeholder="Message your assistant..."
  showReasoning={false}
  onActivityChange={(active) => setAgentBusy(active)}
/>
```

`Chat` also accepts `className` and `disabled`. Omit optional props to use the
defaults. Use `AgentProvider` directly when building a custom interface with
hooks such as `useAgentState` and `useAgentActions`; those hooks must be rendered
inside the provider. See the React package README for hook and store details.

## Supported experiences

The panel includes safe Markdown, streaming, optional reasoning, compact tool
disclosures, approvals, scoped errors, cancellation, an anchored composer, and
scroll-to-latest. Light and dark styles inherit host semantic tokens.

Provide `respondToInterrupt`, `continueRun`, and `cancelRun` only when your
application supports them. Approval values stay opaque and are returned unchanged.
Optional `adapter.attachments` enables file/image selection, previews, upload
status, retry, and removal. Your application owns storage, permissions, limits,
and conversion into model input.

## Restore conversations

Load and normalize saved messages in the consuming app, then hydrate a fresh
store before streaming:

```tsx
import { AgentStore } from "@agentdock-ai/react";

const store = new AgentStore();
store.hydrateHistory({ messages: normalizedMessages, resumeState });
<Chat adapter={chatAdapter} store={store} />;
```

Messages use canonical `messageId`, `role`, and `content`. Optional `resumeState`
is a fresh native waiting-state seed, such as `runtime.getResumeState(threadId)`,
with `runId: null`. The adapter targets your authorized thread for approvals and
static continuation. Hydration is rejected during active execution.

For a custom interface, install the runtime package with your app's package
manager. With npm:

```sh
npm install @agentdock-ai/react react
```

Then use `AgentProvider`, `AgentStore`, `useAgentState`, `useAgentStore`,
`useAgentActions`, and `selectRenderModel`. See the
[UI README](https://github.com/agentdock-ai/agentdock-ui#readme) for the full surface.
